Slow LLM responses: the vendor's fix targeted the wrong component

Production case study. Internal hostnames and identifiers are omitted.

Situation
LLM responses were slow. The vendor had scaled the auth service from 1 to 10 replicas.
Evidence
An approved concurrency test (180 requests, 0 errors) and vLLM metrics showed the bottleneck was long-prompt prefill on a single GPU.
Decision
Management approved my proposal to serve a second model replica on GPU capacity I had measured as allocated but idle.

How I worked

  • The LLM platform was managed by a vendor on Kubernetes, so I changed nothing on it. I got approval from the AI team and the vendor contact for a controlled concurrency test.
  • I read the vLLM serving metrics next to the test results. Latency grew with prompt length, not with the number of requests: the time went into prefilling long prompts on a single GPU. More auth replicas could not change that.
  • I had already measured GPU capacity that was allocated but idle. I wrote the finding up as a one-page recommendation: a second model replica on that capacity.
  • Management approved it. I don't quote a latency improvement here: that number only exists once the replica is live and measured again.

Check the method yourself

On my own time I rebuilt the same method with a public model on a CPU-only laptop: github.com/mtbagatur/llm-serving-loadlab. Same pattern: prompt length explained latency better than concurrency, and a second replica on idle cores gave x1.49 throughput at 8 requests in flight. It is a CPU stand-in, not the GPUs from work, and the repo says so.

Takeaway

Don't argue opinions. Run a small agreed test, show the data, and give one clear recommendation people can say yes to.
